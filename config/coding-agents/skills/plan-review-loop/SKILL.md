# 実装計画のレビュー・改善ループ

## 前提

この skill は、実装計画を作ったセッションで起動する前提にする。
実装計画を作った経緯を知っていると、指摘の妥当性を判定しやすいためである。
会話の文脈が大きくなっているときは、`/compact` してから起動し直すようユーザーに勧める。
`--reviewer claude` でレビュアを Agent ツールで起動するので、Claude Code で使う。

## 手順

### 1. 下準備をする

第1引数を実装計画ファイル、第2引数を要件ファイル（実装計画の元になった Issue など。任意）とする。
実装計画ファイルが無ければユーザーに確認する。

`--reviewer` を省略したら `codex` とする。
`codex` のときは、`codex --version` と `codex login status` で Codex CLI がインストール・認証済みか確かめ、使えなければユーザーに確認する。
`claude` を指定されたら、実装計画を作ったモデルと同じ系列なので、作ったときに見落とした問題をレビューでも見落としやすい、と一言伝えてから進む。

作業ファイルの置き場所として `_local/plan-review-loop/<実装計画ファイル名>/` を作る。
ここに各ラウンドの指摘 `round-<N>.md` と、採否の台帳 `ledger.md` を置く。
`ledger.md` は、レビュアにパスを渡すので、空のファイルとして先に作っておく。

### 2. レビュアへのプロンプトを組み立てる

この skill のディレクトリにある `reviewer-prompt.md` を読み、そのテンプレートからプロンプトを作る。
自分でプロンプトを書き起こさない。

テンプレートに加える変更:

- `{{…}}` のプレースホルダを、実際の値で埋める
- 要件ファイルが無ければ、「要件:」の行を消す
- Codex に渡すときは、末尾に「確認や質問は不要です。具体的な提案まで自主的に出力してください。」の一文を足す。
  これが無いと、Codex が確認を返して止まり、レビュー結果が出ないことがある

### 3. レビュアにレビューさせる

レビュアに、毎ラウンド新しいセッションでレビューさせる。
過去の経緯は台帳で渡す。
Codex でも、`codex exec resume` で前のラウンドのセッションを再開しない。

レビュアごとの呼び出し方:

- `--reviewer codex`（既定）: リポジトリのルートで、次の形で Codex を実行する。
  `< /dev/null` が無いと標準入力待ちで止まる。
  数分以上かかることがあるので、コマンドのタイムアウトは長めにする。

  ```sh
  codex exec --sandbox read-only --cd <リポジトリのルート> \
    -o _local/plan-review-loop/<実装計画ファイル名>/round-<N>.md \
    "<プロンプト>" < /dev/null
  ```

- `--reviewer claude`: Agent ツールを `subagent_type: general-purpose` で呼び出す。
  結果を `round-<N>.md` に保存する。

### 4. 指摘を仕分ける

`round-<N>.md` を読み、指摘を仕分ける。

#### 4.1 レビュー結果を使えるか確かめる

仕分ける前に、「確かめた範囲」を確認する。
そこに実装計画ファイルが挙がっていないとき、または要件ファイルがあるのにそれが挙がっていないときは、そのラウンドの結果を使わず、手順3からやり直す。
実装計画や要件を読んだと確かめられないレビュー結果は、`APPROVED` でも仕分けの根拠にできないためである。
やり直しはラウンド数に数えない。
やり直しても挙がらなければ、ユーザーに確認する。
挙がっていれば、指摘ゼロでもやり直さずにそのまま使う。
指摘ゼロは正常な結果である。

判定と指摘が食い違っていれば（`APPROVED` なのに high か medium の指摘がある）、判定ではなく指摘のほうを信じて仕分ける。

#### 4.2 修正必須の指摘を選ぶ

根拠が示されていない指摘や、実コード・要件と食い違う指摘は却下する。
台帳で却下済みの指摘が、新しい根拠なしに再び出たときも却下する。

残った指摘のうち、修正必須にする条件:

- 重大度が high か medium
- 種類が correctness・requirement_gap・missing_reference・migration_risk・verification_gap のいずれか

それ以外の指摘（low、スタイル、将来の拡張）は直さず、手順7の報告に回す。

#### 4.3 仕分け案をユーザーに確認する

次のどれかに当たれば、仕分け案（4.2 で決めた各指摘の採否と理由）をユーザーに見せ、確認を取ってから進む。
どれにも当たらなければ、確認せずに進む。
指摘が1件も無ければ、条件に当たっても確認しない。

確認する条件:

- 1ラウンド目
- 台帳にまだ無い high の指摘が出た（却下するものも含む）

仕分けに迷った指摘は、採否を「要確認」とする。
上の条件に当たって確認するときは、仕分け案と一緒に見せる。
当たらなければ、手順7の報告でまとめて見せる。
「要確認」の指摘は、ユーザーが採否を決めるまで修正必須に数えず、直さない。
確認のためだけにループを止めない。

#### 4.4 採否を台帳に記録する

各指摘の採否と理由を `ledger.md` に追記する。
レビュアは毎ラウンド 1 から番号を振り直す。
そのため台帳には、ラウンド番号を付けて `R<N>-1` のように記録する。

### 5. 終了するかを判定する

次のどれかに当たれば、実装計画を直さずに手順7に進む。
レビューされないままの修正を残さないためである。

終了する条件:

- 4.2 で修正必須にした指摘がゼロ
- 3ラウンドに達した
- 前のラウンドで修正必須にした指摘が、直したあとも同じ内容で再び出た（停滞）。
  同じ指摘かは、台帳と照らして判断する

### 6. 実装計画を直す

4.2 で修正必須にした指摘に沿って、実装計画ファイルを直す。
直す前後に `git status` で、実装計画ファイル以外に変更が無いか確認する。
そのあと実装計画全体を読み直し、次の点を確かめて、見つかれば直す。
指摘箇所だけ直すと、他の箇所に残った同種の問題や、修正で生じた食い違いが次のラウンドで新しい指摘になり、収束しにくくなるためである。

確かめる点:

- 同じ原因・同じパターンの問題が他の箇所にないか
- 修正後の内容と食い違う記述（用語・前提・手順・参照）が残っていないか

直し終えたら、手順2に戻る。

### 7. 結果をユーザーに報告する

報告に含めるもの:

- 終了理由（修正必須の指摘がゼロ・上限・停滞）と、回したラウンド数
- 各指摘の仕分け結果（修正必須・却下・直さずに回した）と、その理由
- 上限や停滞で終わったときに残った修正必須の指摘と、それに対する Claude の見解
- 最終ラウンドの「確かめられなかった範囲」

上限や停滞で終わったときは、収束したと報告しない。

実装計画の最終承認はユーザーが行う。
承認されたら、`impl-review-loop` に実装計画ファイルを渡して実装するよう案内する。
承認されずに実装計画を直すことになったら、直したあとでこの skill をもう一度起動し、レビューし直すよう案内する。
レビューされないままの修正を残さないためである。

## ルール

- メインのセッションは実装計画をレビューしない。
  レビューは必ずレビュアに任せ、メインのセッションは仕分けと修正だけを担う。
- このループで変更してよいのは実装計画ファイルだけ。
