# 実装のレビュー・改善ループ

## 前提

この skill は、レビュー済みの実装計画を実装するときに使う。
実装と修正は実装役のサブエージェントに任せるので、起動するセッションに実装計画を作ったときの文脈が残っていてもかまわない。

## 手順

### 1. 下準備をする

第1引数を実装計画ファイルとする。
実装計画ファイルが無ければユーザーに確認する。

`--reviewer` を省略したら `codex` とする。
`codex` のときは、`codex --version` と `codex login status` で Codex CLI がインストール・認証済みか確かめ、使えなければユーザーに確認する。
`claude` を指定されたら、実装役と同じ系列なので、実装役が見落とした問題をレビューでも見落としやすい、と一言伝えてから進む。

`git status` で未コミットの変更があれば、ユーザーに確認する。

作業ファイルの置き場所として `_local/impl-review-loop/<実装計画ファイル名>/` を作る。
ここに各ラウンドの指摘 `round-<N>.md` と、採否の台帳 `ledger.md` を置く。
`ledger.md` は、レビュアにパスを渡すので、先に作っておく。
開始時点のコミット（`git rev-parse HEAD`）を `ledger.md` の先頭に記録する。

### 2. 検証コマンドを決める

実装計画を読み、検証コマンド（テスト・型チェック・lint）を決める。
実装計画に書いてあればそれを使う。
無ければ、次の順に探す。

- `AGENTS.md`・`CLAUDE.md`
- `README`・`CONTRIBUTING`
- CI の設定（`.github/workflows` など）
- `package.json`・`Makefile` などのビルド設定

決まらなければユーザーに確認する。

### 3. 実装役に実装させる

この skill のディレクトリにある `implementer-prompt.md` を読み、そのテンプレートからプロンプトを作る。
自分でプロンプトを書き起こさない。
`{{…}}` のプレースホルダは、実際の値で埋める。

Agent ツールを `subagent_type: general-purpose` で呼び出し、実装役を起動する。
以降の修正も、この実装役に SendMessage で続きとして依頼する。
修正のたびに新しい実装役を起動すると、毎回コードを読み直すコストがかかるためである。

実装役が `BLOCKED` を返したら、その質問をユーザーに確認し、答えを添えて同じ実装役に続きを依頼する。
実装役は途中でユーザーに確認できないので、この形で補う。
ユーザーの答えと、それで決めた実装計画からの逸脱は、`ledger.md` に記録する。
レビュアが、ユーザーの決めた逸脱を実装計画に反する変更として指摘しないようにするためである。

実装役が、実装計画そのものの誤りを `BLOCKED` で報告したときも、ユーザーに確認する。
実装計画を直すことになったら、ループを止める。
`plan-review-loop` で実装計画を直してから、この skill を起動し直すよう案内する。

### 4. 検証コマンドを実行する

実装役が `DONE` を返したら、手順2で決めた検証コマンドを、メインのセッションが自分ですべて実行する。
実装役の「通った」という報告だけでは、実装が終わったと判断しない。

通らなければ、失敗した出力を添えて同じ実装役に修正を依頼し、もう一度実行する。
3回直させても通らなければ、そこで止めてユーザーに確認する。
通らない状態ではレビューに進まない。

### 5. レビュアへのプロンプトを組み立てる

この skill のディレクトリにある `reviewer-prompt.md` を読み、そのテンプレートからプロンプトを作る。
自分でプロンプトを書き起こさない。

テンプレートに加える変更:

- `{{…}}` のプレースホルダを、実際の値で埋める
- Codex に渡すときは、末尾に「確認や質問は不要です。具体的な提案まで自主的に出力してください。」の一文を足す。
  これが無いと、Codex が確認を返して止まり、レビュー結果が出ないことがある

レビュアの判断が引きずられないよう、実装役の報告や検証コマンドの出力は渡さない。

### 6. レビュアにレビューさせる

レビュアに、毎ラウンド新しいセッションでレビューさせる。
過去の経緯は台帳で渡す。
Codex でも、`codex exec resume` で前のラウンドのセッションを再開しない。

レビュアごとの呼び出し方:

- `--reviewer codex`（既定）: リポジトリのルートで、次の形で Codex を実行する。
  `< /dev/null` が無いと標準入力待ちで止まる。
  数分以上かかることがあるので、コマンドのタイムアウトは長めにする。

  ```sh
  codex exec --sandbox read-only --cd <リポジトリのルート> \
    -o _local/impl-review-loop/<実装計画ファイル名>/round-<N>.md \
    "<プロンプト>" < /dev/null
  ```

- `--reviewer claude`: Agent ツールを `subagent_type: general-purpose` で呼び出す。
  結果を `round-<N>.md` に保存する。

### 7. 指摘を仕分ける

`round-<N>.md` を読み、指摘を仕分ける。

#### 7.1 レビュー結果を使えるか確かめる

仕分ける前に、「確かめた範囲」を確認する。
そこに実装計画ファイルか差分が挙がっていないときは、そのラウンドの結果を使わず、手順6からやり直す。
実装計画や差分を読んだと確かめられないレビュー結果は、`APPROVED` でも仕分けの根拠にできないためである。
やり直しはラウンド数に数えない。
やり直しても挙がらなければ、ユーザーに確認する。
挙がっていれば、指摘ゼロでもやり直さずにそのまま使う。
指摘ゼロは正常な結果である。

判定と指摘が食い違っていれば（`APPROVED` なのに high か medium の指摘がある）、判定ではなく指摘のほうを信じて仕分ける。

#### 7.2 修正必須の指摘を選ぶ

根拠が示されていない指摘や、実装計画・実コードと食い違う指摘は却下する。
台帳で却下済みの指摘が、新しい根拠なしに再び出たときも却下する。

残った指摘のうち、修正必須にする条件:

- 重大度が high か medium
- 種類が requirement_gap・correctness・out_of_scope・weakened_check のいずれか

それ以外の指摘（low、untested_edge_case など）は直さず、手順10の報告に回す。

#### 7.3 仕分け案をユーザーに確認する

次のどれかに当たれば、仕分け案（7.2 で決めた各指摘の採否と理由）をユーザーに見せ、確認を取ってから進む。
どれにも当たらなければ、確認せずに進む。
指摘が1件も無ければ、条件に当たっても確認しない。

確認する条件:

- 1ラウンド目
- 台帳にまだ無い high の指摘が出た（却下するものも含む）
- 修正必須の指摘が、台帳に記録したユーザーの決定と食い違う

仕分けに迷った指摘は、採否を「要確認」とする。
上の条件に当たって確認するときは、仕分け案と一緒に見せる。
当たらなければ、手順10の報告でまとめて見せる。
「要確認」の指摘は、ユーザーが採否を決めるまで修正必須に数えず、直さない。
確認のためだけにループを止めない。

#### 7.4 採否を台帳に記録する

各指摘の採否と理由を `ledger.md` に追記する。
レビュアは毎ラウンド 1 から番号を振り直す。
そのため台帳には、ラウンド番号を付けて `R<N>-1` のように記録する。

### 8. 終了するかを判定する

次のどれかに当たれば、実装役に直させずに手順10に進む。
レビューされないままの修正を残さないためである。

終了する条件:

- 7.2 で修正必須にした指摘がゼロ
- 3ラウンドに達した
- 前のラウンドで修正必須にした指摘が、直させたあとも同じ内容で再び出た（停滞）。
  同じ指摘かは、台帳と照らして判断する

### 9. 実装役に直させる

7.2 で修正必須にした指摘を、同じ実装役に SendMessage で続きとして渡し、直させる。

続きの依頼に含めるもの:

- 修正必須にした各指摘の根拠・内容・修正案
- 指摘箇所だけでなく、同じ原因・同じパターンの問題が他の箇所にないかも確かめて直すこと
- `implementer-prompt.md` と同じ形式で返すこと

指摘箇所だけ直すと、他の箇所に残った同種の問題が次のラウンドで新しい指摘になり、収束しにくくなるためである。

実装役が `DONE` を返したら、手順4に戻る。

### 10. 結果をユーザーに報告する

報告に含めるもの:

- 実行した検証コマンドと、最後に実行したときの結果
- 終了理由（修正必須の指摘がゼロ・上限・停滞）と、回したラウンド数
- 各指摘の仕分け結果（修正必須・却下・直さずに回した）と、その理由
- 上限や停滞で終わったときに残った修正必須の指摘と、それに対する Claude の見解
- 最終ラウンドの「確かめられなかった範囲」

上限や停滞で終わったときは、収束したと報告しない。

実装の最終承認とコミットは、ユーザーが行う。

## ルール

- メインのセッションは、実装もレビューもしない。
  実装と修正は実装役に、レビューはレビュアに任せ、メインのセッションは検証・仕分け・ユーザーへの確認だけを担う。
- メインのセッションも実装役も、コミットしない。
